# Workers KV 缓存策略与开发计划（减少 D1 行读取）

目标：在 `inpageedit-analytics-next` 中引入/完善 Workers KV 缓存，**显著降低 D1 的行读取与聚合扫描成本**，同时保证可接受的数据新鲜度与一致性。

## 背景与关键约束

- **数据写入入口**：`POST /api/v6/submit`（`server/api/v6/submit.post.ts`）会把 usage 写入 `event_log`（`server/utils/logUsages.ts`）。
- **写入时间窗口约束**：提交的每条 usage 必须在"最近 1 小时内"（接口里校验 `ts` 在 `now-1h ~ now`）。这意味着：
  - 对任何查询窗口，只要 **`end <= now - 3600s`**，这个窗口的结果就可以视为"**不可变（不会再被写入补齐）**"，因此可做**长 TTL/近似永久缓存**。
- **当前表结构与索引**（`db/schema.ts`）：
  - `event_log` 只有 `createdAt` 的索引（`ix_event_time`），而大量查询会按 `siteId/userId + createdAt` 过滤并聚合/排序。
  - 因此在短期内，**缓存对聚合类接口的收益非常高**（减少扫描与聚合开销）。

## API 接口盘点（按路径）

以下均为 Nuxt Nitro 文件路由（`server/api/**` → `/api/**`）。

### 写入类

- **`POST /api/v6/submit`**：写入事件、确保 `wiki_site/wiki_user` 存在
  - 触发：`ensureWikiSiteByPayload`、`ensureWikiUserByPayload`、`logUsages`
  - 读写：D1（查/插/更新站点与用户；批量插入 event_log）
  - **缓存行为**：写入成功后更新版本号 `ipea:ver:global`、`ipea:ver:site:<id>`、`ipea:ver:user:<id>`
- `POST /api/submit`：v5 deprecated（仅返回错误）

### 明细类（读多但可短缓存）

- **`GET /api/v6/usage/recent`**：最近事件明细（支持 `siteId/userId` + 分页）
  - 读：`event_log` + join `wiki_user/wiki_site`，按 `createdAt desc`
  - **缓存策略**：仅缓存前 100 条（`offset <= 100`），TTL 30 秒，带版本号

### 聚合/统计类（读多且最该缓存）

- **`GET /api/v6/usage/total`**：总量/去重用户数/去重站点数（支持 `siteId/userId/start/end`）
  - 读：3 次聚合查询（`count()` / `countDistinct(userId)` / `countDistinct(siteId)`）
  - **缓存策略**：
    - 不可变窗口（`end <= now-3600s`）：7 天 TTL
    - 混合/热窗口：5 分钟/30 秒 TTL + 版本号
    - **预计算快路径**：命中 `last_1d/7d/30d` 窗口时直接读 `ipea:precalc:usage:total:*`
- **`GET /api/v6/usage/daily`**：按天统计（支持 `siteId/userId/start/end`，最大 180 天）
  - 读：`strftime` 分组聚合
  - **缓存策略**：`start/end` 对齐到天边界，不可变窗口长 TTL，其他中 TTL + 版本号
- **`GET /api/v6/usage/user`**：用户总量 + feature 分组（`userId`）
  - **缓存策略**：5 分钟 TTL，按 `userId` 版本号失效
- **`GET /api/v6/usage/site`**：站点总量（`siteId`）
  - **缓存策略**：5 分钟 TTL，按 `siteId` 版本号失效
- **`GET /api/v6/leaderboard/user`**：用户排行榜（支持 `siteId/start/end` + 分页）
  - **缓存策略**：
    - 通用窗口：按窗口类型分配 TTL + 版本号
    - **预计算快路径**：全局榜单（无 `siteId` 过滤）命中 `last_1d/7d/30d` 时直接读 `ipea:precalc:leaderboard:user:*`
- **`GET /api/v6/leaderboard/site`**：站点排行榜（支持 `start/end` + 分页）
  - **缓存策略**：
    - 通用窗口：按窗口类型分配 TTL + 版本号
    - **预计算快路径**：命中 `last_1d/7d/30d` 时直接读 `ipea:precalc:leaderboard:site:*`

### 搜索类（读少，可轻缓存）

- **`GET /api/v6/search/user`**：按 `siteApi+mwUserId` 精确查 / 按 `userName` 前缀查（支持 `siteId/siteApi` 过滤）
- **`GET /api/v6/search/site`**：按 `siteName` 前缀 / `siteUrl` 前缀查

### 其他

- `GET /api`：API banner
- `GET /api/_dev/**`：开发用路由，可不做任何缓存处理，生产环境自动 403
- `GET /api/**` fallback：404
- 跳转路由（非 `/api`）：`GET /_redirect/site`、`GET /_redirect/user` 已设置 `cache-control: max-age=2592000`，可考虑做永久缓存

## 缓存总体思路

### 两层缓存（已落地）

1. **KV 响应缓存（Response Cache）**：对"聚合/排行/统计"接口做 KV 缓存，按参数构造 key，配合 TTL 与"不可变窗口"规则。
2. **KV 物化结果/预计算（Materialized Cache）**：用 cron 定时预计算常用窗口（如 1d/7d/30d）并落 KV；API 命中这些窗口时直接读 KV，完全绕开 D1 聚合。

> 备注：Workers KV 不具备强一致与原子自增，短期不建议用 KV 做实时精确计数（除非接受近实时误差并定期对账）。本计划用"短 TTL + 版本号失效 + cron 预热"取得高收益与低复杂度的平衡。

## Key 规范与参数归一化

### 统一 key 前缀

- `ipea:v6:<group>:<endpoint>:...` - 响应缓存
- `ipea:precalc:<group>:<endpoint>:...` - 预计算缓存
- `ipea:ver:<type>:<id>` - 版本号

示例：

- `ipea:v6:usage:total:site=12:user=0:start=0:end=0:ver=1700000000-0-0`
- `ipea:v6:leaderboard:user:site=0:start=1700000000:end=1700600000:limit=10:offset=0:ver=1700000123-0-0`
- `ipea:precalc:usage:total:last_7d`
- `ipea:ver:global`
- `ipea:ver:site:42`

### 参数归一化（避免 key 爆炸）

- **时间戳统一为秒**（现有接口已做毫秒 → 秒转换）
- 对按天聚合的接口（`usage/daily`）：
  - 将 `start/end` **对齐到天边界**（例如 `start` 向下取整到 00:00，`end` 向上取整到 23:59:59），减少同义请求的 key 分裂
- 对排行榜接口：
  - UI 常用窗口固化为 `last_1d/last_7d/last_30d/all_time`，把自由 `start/end` 作为"高级查询"路径（仍可缓存，但 TTL 更短）

## TTL 规则（核心）

定义：

- `now = floor(Date.now()/1000)`
- `frozenBefore = now - 3600`（由 submit 限制推导：更早的数据不会再被写入）

规则：

- **不可变窗口**：若请求窗口满足 `end <= frozenBefore`
  - **TTL：长**（7 天）
  - **不需要**写入触发的失效版本号（因为不会再变）
- **混合窗口**：`start < frozenBefore < end`
  - **TTL：中**（5 分钟）
  - 加入"版本号"用于在写入后快速失效
- **热窗口**：`start >= frozenBefore`（完全落在最近 1 小时）
  - **TTL：短**（30 秒）
  - 必须加入"版本号"降低脏读时间

## 失效机制（避免全量扫描删除）

KV 不适合枚举删除大量 key，因此采用"**版本号参与 key 构造**"的软失效方式。

### 版本号 key

- `ipea:ver:global`
- `ipea:ver:site:<siteId>`
- `ipea:ver:user:<userId>`

写入时（`POST /api/v6/submit` 成功后）：

- `KV.put(ipea:ver:global, now.toString())`
- `KV.put(ipea:ver:site:<siteId>, now.toString())`
- `KV.put(ipea:ver:user:<userId>, now.toString())`

读取时（仅对"混合/热窗口"）：

- 先读对应版本号（没有则当作 `0`）
- 将版本字符串拼入缓存 key，做到"写入后立刻换 key"

> 说明：这里用"更新时间戳"而不是"自增计数"，避免 KV 原子性问题；多并发写入时"最后写入 wins"完全可接受。

## 各接口策略（已落地）

### `GET /api/v6/usage/total`

- **缓存价值**：最高（3 次聚合）
- **实现**：
  - 采用"不可变窗口长 TTL"规则（`end <= now-3600`）
  - 对热/混合窗口加入 `global/site/user` 版本号
  - **预计算快路径**：全局统计（无 `siteId/userId` 过滤）命中 `last_1d/7d/30d` 时直接读预计算 KV
- **响应标记**：返回 `cached: boolean` 和 `precalc: boolean`

### `GET /api/v6/usage/daily`

- **缓存价值**：高（按天 group by）
- **实现**：
  - `start/end` 天边界归一化后做 KV 缓存
  - 不可变窗口：长 TTL；其他：中 TTL + 版本号

### `GET /api/v6/leaderboard/user` / `site`

- **缓存价值**：最高（group by + order by count）
- **实现**：
  - 对自由 `start/end` 做 KV 响应缓存（中/短 TTL + 版本号）
  - **预计算快路径**：全局榜单（无 `siteId` 过滤）且第一页（`offset=0, limit<=50`）命中 `last_1d/7d/30d` 时直接读预计算 KV
- **响应标记**：返回 `cached: boolean` 和 `precalc: boolean`

### `GET /api/v6/usage/user` / `site`

- **缓存价值**：中高（仍需聚合）
- **实现**：KV 响应缓存 + 版本号（5 分钟 TTL）
- **响应标记**：返回 `cached: boolean`

### `GET /api/v6/usage/recent`

- **缓存价值**：中（明细分页本质上是"时间线"）
- **实现**：
  - 仅缓存**前几页**（`offset <= 100`）且 TTL 很短（30 秒）
  - 加 `global/site/user` 版本号，避免写入后"第一页还显示旧数据"
- **响应标记**：返回 `cached: boolean`

## cron 预计算（把最贵的查询变成 0 D1 读取）

配置：`wrangler.jsonc` 已配置每 5 分钟触发 cron（`"crons": ["*/5 * * * *"]`）

实现：`server/plugins/cron.ts` 处理 `cloudflare:scheduled` 事件

预计算内容：

1. **常用窗口 leaderboard**
   - 全站：`last_1d/7d/30d` 的站点榜与用户榜（Top 50）
   - KV key: `ipea:precalc:leaderboard:site:last_1d` / `ipea:precalc:leaderboard:user:last_1d`
2. **预计算概览统计**
   - `usage/total` 的常用窗口：`last_1d/7d/30d/all_time`
   - KV key: `ipea:precalc:usage:total:last_1d`

预计算数据 TTL：2 天（确保 cron 故障时仍有缓存）

## 风险与注意事项

- **KV 一致性**：KV 为最终一致，适合缓存与预计算，不适合作为精确强一致数据源。
- **key 数量与成本**：自由 `start/end/limit/offset` 会导致 key 膨胀，必须做参数归一化并限制热点页缓存。
- **击穿与并发**：KV 缺少可靠的"分布式锁"，建议依赖 TTL + 预热 +（可选）同 isolate 内 singleflight 降低瞬时重复计算。
